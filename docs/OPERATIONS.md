# 운영 및 개발 가이드

## 로컬 실행

Node.js 24 이상과 npm을 사용합니다. 테스트는 Node의 내장 TypeScript 실행 기능을 사용합니다.

```bash
npm ci
cp .env.example .env.local
npm run dev
```

`.env.local`에 Supabase URL과 anon key를 입력합니다. 파일을 커밋하지 않습니다.

- `AI_PROVIDER=mock`: 한국어·영어 키워드 기반 데모 분석. 외부 AI API나 유료 키 없이 수동 분석과 검토·초안 흐름을 사용할 수 있습니다.
- `SUPABASE_SERVICE_ROLE_KEY`: 문의 접수 시 서버 자동 분석에만 필요합니다. 없으면 문의는 정상 접수되고 상담원이 수동 분석합니다. 브라우저에 전달하지 않습니다.
- `AI_CONFIDENCE_REVIEW_THRESHOLD`: 기본 0.7. 빈 값과 잘못된 값은 기본값을 사용합니다. 0은 유효한 값입니다. 환불·보안 등 위험 신호는 신뢰도와 관계없이 검토 대상으로 보냅니다.
- `OPENAI_API_KEY`, `AI_MODEL`: 향후 실제 provider 연결을 위한 예약 설정입니다. 현재 OpenAI provider는 구현되지 않았으므로 `AI_PROVIDER=openai`로 전환하지 않습니다.

## 데이터베이스 적용 순서

새 데이터베이스에서는 아래 순서로 SQL을 적용합니다. 회원가입을 공개하기 전에 보강 마이그레이션까지 적용해야 합니다.

1. `docs/SUPABASE_SCHEMA.sql`
2. `docs/AI_SCHEMA_MIGRATION.sql`
3. `supabase/migrations/20260906094054_harden_support_workflow.sql`
4. 필요한 경우에만 `docs/DEMO_ACCOUNTS.sql` — 공개 데모 전용

기존 데이터베이스에 기본 스키마와 AI 스키마가 이미 있으면 **3번만 적용**합니다. 더 오래된 DB에 `ticket_number`가 없다면 `docs/TICKET_NUMBER_MIGRATION.sql`을 먼저 적용합니다. 기본 스키마를 기존 DB에 다시 실행하지 않습니다.

현재 저장소는 기존 수동 SQL에서 마이그레이션 관리로 넘어가는 중입니다. `supabase/migrations`는 전체 초기 스키마가 아니라 기존 DB에 적용할 증분 변경을 담습니다. 초기 SQL이 적용되지 않은 DB에 `db push`만 실행하면 안 됩니다. 이후 변경은 Supabase CLI의 `migration new`로 생성합니다.

### 이번 마이그레이션의 영향

- 기존 프로필·문의·답변·분석을 삭제하지 않습니다. 기존 계정의 역할도 변경하지 않습니다.
- 가입 시 사용자 입력 역할을 무시하고 항상 customer로 생성합니다. 상담원/관리자 승격은 신뢰할 수 있는 운영자 SQL 또는 서버 관리 절차로만 수행합니다.
- 일반 사용자는 자신의 이름만 수정할 수 있습니다.
- 문의의 AI 비정규화 필드는 브라우저의 직접 SELECT에서 제외합니다. 화면은 `ticket_workspace` 보안 뷰를 사용합니다. 뷰는 호출자의 RLS를 그대로 따르며 고객에게 AI 결과를 반환하지 않습니다.
- 상태·배정·답변·AI 저장·검토는 `support_ticket_command`를 사용합니다. 기존 브라우저 직접 UPDATE/INSERT 및 `create_ticket_reply` 호출은 차단합니다.
- 원자적 저장을 수행하는 구현 함수는 공개 API 스키마 밖의 `supportflow_private`에 있으며, 인증 사용자와 실제 프로필·담당자를 확인합니다. 이 스키마를 Supabase의 exposed schemas에 추가하지 않습니다.
- 입력 길이 CHECK는 `NOT VALID`로 추가해 기존 데이터는 보존하되 신규/수정 데이터부터 검증합니다. 오래된 데이터가 현재 입력 제한에 맞는지는 별도로 점검해야 합니다.

**배포 시 SQL과 앱을 함께 전환해야 합니다.** 이전 앱은 직접 쓰기 권한을 사용하고, 새 앱은 새 뷰/RPC를 필요로 합니다. 먼저 스테이징 DB에서 적용·검증하고, 운영은 짧은 유지보수 시간에 SQL 적용 후 새 앱을 배포합니다. 이번 로컬 작업만으로 원격 DB나 배포 사이트가 변경되지는 않습니다.

기존 환경에서 이미 가입된 계정은 신뢰할 수 있는 관리자가 검토해야 합니다. 새 정책이 과거의 잘못된 역할 부여까지 자동으로 판별하거나 되돌리지는 않습니다.

## 구조와 권한

- Next.js App Router가 서버에서 로그인과 역할별 경로 접근을 확인합니다.
- Supabase Auth + RLS가 데이터 접근 범위를 제한합니다. UI의 역할 표시를 권한의 근거로 사용하지 않습니다.
- `features/*/api`는 데이터 접근, `hooks`는 TanStack Query 캐시, `components`는 화면, `schemas`는 입력 검증을 담당합니다.
- React Hook Form + Zod가 폼 오류와 pending 상태를 관리합니다.
- Zustand는 사이드바 같은 UI 상태에만 사용합니다.
- 문의·검토 큐의 검색/필터/페이지는 URL에 저장합니다. 목록은 서버 페이지네이션을 사용합니다.
- 변경 성공 시 관련 목록·상세·대시보드 캐시를 무효화합니다. 담당자 변경 시 AI 접근 범위와 담당자 통계도 새로 조회합니다.

## AI 처리 흐름

1. 상담원의 수동 요청은 `POST /api/tickets/[id]/analysis`로 전달합니다.
2. 서버가 세션과 역할, 문의 접근 권한을 확인합니다.
3. 활성 `ticket-triage` 프롬프트 버전과 provider를 선택합니다.
4. provider의 unknown 출력은 Zod로 검증합니다. 잘못된 JSON/스키마는 신뢰도 0, 초안 없음, 검토 필요인 fallback으로 변환합니다.
5. 위험 신호와 신뢰도 기준을 적용하고 최종 결과를 다시 검증합니다.
6. DB 트랜잭션이 분석·최신 포인터·활동 로그를 함께 저장합니다. 문의 행 잠금과 예상 최신 분석 ID 검사로 경합을 감지합니다.
7. 상담원이 확인·수정·제외하거나 검토를 요청합니다. 과거 분석은 최신 결과를 덮어쓸 수 없습니다. 제외하면 답변 초안과 상태/우선순위 제안을 제거합니다.
8. 초안을 작성란에 가져오는 것과 발송은 별도 작업입니다. 공개 답변 제출 시에만 상태 변경과 로그가 함께 저장됩니다.

고객 인입 자동 분석은 서버 service-role 클라이언트로 실행되며, 고객 소유의 아직 분석되지 않은 문의에만 허용됩니다. 자동 분석 실패는 문의 접수를 취소하지 않습니다.

검토 큐와 감정·긴급도·평균 신뢰도는 문의별 **최신 분석**을 집계하며 검토에서 제외된 결과는 감정·긴급도·평균 신뢰도에서 제외합니다. 최근 7일 분석 횟수는 재분석을 포함한 실제 생성 횟수입니다. 현재 통계는 페이지를 모두 읽어서 집계하므로 대규모 운영에서는 DB 집계 RPC로 전환하는 것이 다음 확장 지점입니다.

## 실제 기능 범위

- 문의함·상세·AI 검토·대시보드·리포트·처리 흐름: 현재 계정이 접근할 수 있는 실제 DB 데이터 사용.
- 자동화: 실제 적용되는 규칙의 읽기 전용 설명. 사용자 정의 규칙 편집기는 제공하지 않음.
- 연동 상태: 관리자만 접근 가능한 설정 여부 화면. 실시간 연결 상태 점검이나 설정 편집 화면은 아님.
- 문의 목록의 응답 목표는 우선순위별 고정 시간(긴급 4h, 높음 8h, 보통 24h, 낮음 48h)과 접수 시각으로 계산한 참고값입니다. 영업시간·계약별 SLA는 반영하지 않습니다.
- 이메일 수신·Slack·CRM·SLA 측정 엔진: 미제공. 성공 상태나 측정 수치를 임의로 표시하지 않음.
- 공개 답변은 기존 제품과 동일하게 문의당 한 번이며 내부 메모는 여러 번 작성 가능.

## 검증

```bash
npm run lint
npm run typecheck
npm test
npm run test:db
npm run build
```

`test:db`는 버전을 고정한 PGlite를 npm 임시 실행 환경에서 사용합니다. 앱의 DB를 추가하거나 원격 Supabase에 연결하지 않습니다. 최초 실행은 다운로드를 위한 네트워크가 필요합니다. PostgreSQL에 최소 Auth 스키마와 역할을 생성한 후 저장소의 SQL과 실제 마이그레이션을 실행합니다.

검증 범위: 가입 역할 위조, 자기 승격, 고객 정보 분리, 상담원/관리자 권한, 서버 자동 분석, 중복 답변, 오래된 분석 경합, 검토 이력, 로그 실패 시 트랜잭션 롤백. 단위 테스트는 mock 결정성·한국어 결과·출력 검증·fallback·검토 기준·페이지네이션을 확인합니다.

PGlite 테스트는 실제 GoTrue 세션 갱신이나 PostgREST 설정을 대체하지 않습니다. 배포 전 스테이징에서 아래를 확인합니다.

1. 고객: 가입 → 문의 생성 → 본인 문의/공개 답변만 조회. AI·내부 메모·다른 고객 문의는 접근 불가.
2. 관리자: 배정/우선순위 변경 → 상담원 조회 범위 반영.
3. 상담원: 분석 → 검토 → 초안 불러오기 → 수정 → 공개 답변 제출.
4. 두 탭에서 재분석/검토 시 최신 결과 유지와 충돌 안내 확인.
5. 검토 큐·리포트·대시보드의 최신 상태 반영 확인.

## 문제 해결

- `ticket_workspace` 또는 `support_ticket_command`를 찾지 못함: 보강 마이그레이션을 아직 적용하지 않은 DB입니다.
- 기존 앱에서 permission denied: DB만 먼저 전환하고 새 앱을 배포하지 않았는지 확인합니다.
- 수동 AI 분석 실패: `AI_PROVIDER=mock`과 활성 `ticket-triage` 프롬프트 버전이 있는지 확인합니다.
- 접수 자동 분석이 실행되지 않음: 서버의 service-role 설정 여부를 확인합니다. 수동 분석은 이 키가 필요하지 않습니다.
- 빌드 중 Google Fonts 다운로드 실패: 네트워크 접근을 확인합니다. 앱은 Next.js font 빌드 시 폰트를 내려받습니다.
- 공개 데모 계정은 실제 고객 데이터 저장에 사용하지 않습니다. 운영 환경에 데모 계정 SQL을 적용하지 않습니다.

## 포트폴리오 설명 예시

- 역할별 티켓 운영과 AI 분류·답변 초안·사람의 검토를 연결한 고객지원 SaaS 구현.
- 서버 인증, RLS·컬럼 권한, DB 트랜잭션과 회귀 테스트로 권한 우회와 부분 저장 문제 보강.
- URL 필터와 TanStack Query 캐시 동기화, 로딩·오류·빈 상태를 포함한 운영 화면 설계.
